Ofox Desktop and CC Switch

This section repeats Ofox pages opened again on that date. Codex CLI and Claude Code stay unverified on this site. scripts/ofox-smoke.py and tests/ofox_smoke.py do not launch either client. A direct Cursor connection stays incompatible, and Cursor is not one of Desktop’s ten tools.

Ofox Desktop

Ofox Desktop says: after sign-in, select installed tools and click Connect. Ofox manages a dedicated key for each selected tool and writes that tool’s own access settings. The hero names Claude Code, Codex, ChatGPT, and OpenClaw, and says those tools share one account and one bill.

The compatibility table on the page is labeled README · 1.5.0. The GitHub README opened the same day says “Supported in 1.5.0.” One-click access is checked for all ten tools: Claude Code, Codex, ChatGPT (Codex mode), OpenCode, Gemini CLI, OpenClaw, Hermes, WorkBuddy, DeepSeek Harness (dsh), and Pi. The ChatGPT row covers Codex mode only and shares Codex configuration and local sessions. Ordinary ChatGPT cloud chats are outside this integration.

Download requirements: macOS 12+ on Apple Silicon, with signed and notarized official releases; Windows 10/11 x64, currently unsigned, so check the source before accepting a SmartScreen warning. The same page’s SoftwareApplication data lists softwareVersion v1.5.3, which is a different field from the 1.5.0 compatibility table. The Desktop download table does not list Linux. The app is free and MIT-licensed. Model, search, and media use are charged at their own prices.

The Codex desktop-app guide says Ofox Desktop and Codex Desktop are different applications. Use one configuration tool at a time so settings are not overwritten. Installing a configuration tool does not itself verify an API connection.

CC Switch

The Codex and Claude Code provider guides both recommend CC Switch, and both also offer Ofox Desktop as the faster setup. The macOS command is:

brew install --cask cc-switch

The same pages also list a macOS .dmg, a Windows .msi, and Linux deb, rpm, and AppImage packages. CC Switch’s stated support is macOS 12+, Windows 10+, and Ubuntu 22.04+ / Debian 11+ / Fedora 34+.

For Codex, switch to the Codex tab. The request URL is https://api.ofox.ai/v1 with no trailing slash, the API format is OpenAI Compatible, and the settings are written to the global config.toml. Claude Code is a client tool here: the request URL is https://api.ofox.ai/anthropic with no trailing slash, the format stays Anthropic Messages (Native), the auth field stays ANTHROPIC_AUTH_TOKEN, and CC Switch writes ~/.claude/settings.json. The general CC-Switch page lists a different API base URL, https://api.ofox.ai/v1. The Claude Code guide and the integration overview use https://api.ofox.ai/anthropic. Match the page for the client being configured.

Manual fields, for reference

Ofox’s integration overview says Codex reads ~/.codex/config.toml. The block below places that overview’s provider fields next to the wire_api = "responses" line from the same overview’s prose. The Codex guide says the CLI uses the OpenAI Responses API, and that not every model supports that format. The sample model id from Ofox’s example is omitted here. Codex CLI stays unverified.

model_provider = "ofoxai"

[model_providers.ofoxai]
name = "OfoxAI"
base_url = "https://api.ofox.ai/v1"
env_key = "OFOXAI_API_KEY"
wire_api = "responses"

env_key is the environment-variable name. Keep the key in the local environment, off public pages.

The Claude Code variables in that same overview match the request URL and auth field on the CC Switch guide:

export ANTHROPIC_BASE_URL=https://api.ofox.ai/anthropic
export ANTHROPIC_AUTH_TOKEN=<OFOXAI_API_KEY>

Claude Code is Anthropic’s coding client. This page does not name a Claude model. Model ids come from the catalog entries that list the protocol in use.

Ofox’s own check. The Claude Code doc says a reply alone does not establish which provider processed the request. Tool calling needs its own test in a disposable project; a text response is not a tool-compatibility test. The Codex Desktop guide says a response plus a matching usage record verifies that request path. They do not independently prove model identity, or tool calling, image input, or structured output.
